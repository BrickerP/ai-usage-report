# 图表模型下钻 Problem Definition（方案 A）

## 结论先行

这次优化要解决的不是“统计维度不够多”，而是：

> 个人维护者在发现一段用量变化后，无法在保留当前时间上下文的情况下，快速从工具归因到具体模型；现有做法迫使他在简洁总览和完整明细之间来回切换、人工关联。

## Look inward：我们正在假设什么

### 已被当前讨论支持

- 模型属于 Codex、Claude Code、Cursor、One API 的下一层，而不是第五种一级统计对象。
- 当前页面结构和视觉语言有价值，不应为模型分析重做成 BI dashboard。
- 独立 cache 时间轨的决策价值低于模型时间分布；全历史 cache 已占总 tokens 的 91.7%，两轨视觉高度重复。
- 用户首先需要快速扫视，只有发现异常或好奇时才需要完整模型明细。

### 仍待原型验证

- 点击工具进入模型态，比永久的“工具 / 模型”切换更自然。
- Top 4 + `Legacy unknown` + `其他 N 个模型` 足以保持趋势可读。
- 用户能够理解“其他”只是视觉汇总，而不是一个真实模型。
- 完整模型清单适合按需出现，不必常驻页面。
- 费用辅轨在模型态仍有足够价值，应随所选工具一起变化。

### 需要主动避免的解法偏见

- 不能因为 ECharts 容易增加 series，就默认“所有模型都画出来”等于完整。
- 不能因为现有模型列表已经存在，就假设它与时间图之间的人工关联足够。
- 不能为了消灭视觉复杂度而隐藏小模型、`Legacy unknown` 或破坏总计守恒。

## Look outward：谁在什么时刻痛

### 主要用户

这个报告的维护者本人：同时使用多种 AI coding 工具、关心 tokens 与估算费用、也会质疑数据是否重复或漏记的个人开发者。

### 典型触发时刻

1. 完成一次较长的编码工作后，想知道主要消耗来自哪个工具和模型。
2. 发现某天柱形或费用突然升高，想追到具体模型。
3. 新模型开始出现，想确认它从哪天起产生了多少用量。
4. 怀疑统计重复、漏算或归属错误，需要从汇总追到精确值。

### 当前凑合办法

- 先在时间图中记住异常日期。
- 再回到工具卡逐项扫描模型累计值。
- 依靠记忆猜测模型与异常日期是否相关。
- 必要时直接查看 `usage.json`、运行 `jq` 或导出后做透视表。

### 谁反而受益于现状

- 实现层面受益：固定 series 最简单，没有下钻状态。
- 只关心工具总量的人受益：图表行为完全静态。

因此新设计必须让默认工具态保持同样直接；模型能力只能按需出现，不能让所有人先经过模型层。

### 功能工作

当我在一段日期范围内看到用量变化时，我想从贡献最大的工具继续追到具体模型，并读取精确 tokens 与费用，从而判断这次变化来自真实使用、模型切换还是统计异常。

### 情感工作

- 我希望相信页面上的总量可解释，而不是面对一堆无法关联的数字。
- 我希望获得“已经找到来源”的确定感，而不是继续怀疑是否双算。
- 我不希望为了一个简单问题进入复杂的数据分析模式。

### 社交工作

当我分享这份公开报告时，希望别人能理解数字由哪些工具和模型组成，并且不会因隐藏数据或口径切换而质疑可信度。

## Top pain points

1. **时间与模型断开**：模型累计值存在，但无法直接解释某一天或某一段走势。
2. **完整与清晰冲突**：14 个 One API 模型全部常驻会不可读，只显示 Top N 又像在隐藏数据。
3. **上下文容易丢失**：进入另一页面或重置日期后，用户要重新寻找原来的异常。
4. **控制重复**：当前时间预设、日期输入、前后移动、Reset 与 slider 同时存在，增加操作选择。
5. **视觉轨道重复**：Total 与 Cache 两条时间图携带大量相同形状，却把真正需要的模型层推到页面之外。

## Proto-persona（待验证）

### “报告维护者”

- **身份**：一人同时使用 Codex、Claude Code、Cursor 和 One API 的开发者。
- **使用频率**：每天快速扫一眼，出现异常时深入查看。
- **触发**：当天费用升高、新模型启用、统计结果与主观使用感受不一致。
- **当前办法**：时间图 + 工具卡 + JSON/JQ 手工对照。
- **最担心**：重复统计、模型归属错误、图表为了简洁而隐藏真实数据。
- **成功时刻**：在原来的日期范围里，一次选择工具即可看出哪些模型造成变化；需要时能继续读到任一小模型的精确值。

## 问题陈述

个人 AI coding 用量维护者需要在保留时间上下文和统计守恒的前提下，从汇总变化追溯到具体模型，因为现有的聚合总览与模型明细彼此分离，而把全部模型永久展开又会破坏页面的快速可读性。

## HMW

我们如何帮助个人维护者从一个异常用量信号自然追到精确模型归因，同时不增加默认页面复杂度、不改变统计口径，也不隐藏低用量模型？

## 可观察的成功信号

### 核心任务

以默认 30 天范围打开报告，用户应能：

1. 在工具总览中找到最高用量日期。
2. 用一次选择进入贡献工具的模型层。
3. 在不改变日期范围的情况下识别主要贡献模型。
4. 用至多再一次操作查看任一低用量模型的精确 tokens 与费用。
5. 返回后恢复相同日期范围的工具总览。

### 可验收指标

- 任一图表状态最多 6 个常驻可见 series，不出现分页图例。
- 所有非零模型名称、tokens 和费用均可在两次操作内访问。
- 下钻、聚焦小模型和返回均不改变当前日期范围。
- 工具态总量等于模型态全部模型之和；`其他` 汇总也必须满足守恒。
- `Legacy unknown` 永远独立显示，不合并进 `其他`。
- Top 4 外仅剩一个模型时直接显示真实名称，不生成 `其他 1`。
- 默认态的信息量不高于当前工具态。
- 移动端宽度不产生横向溢出；模型全量清单允许纵向展开但不横向滚动。
- 图表总高度应低于当前 720px 桌面高度；删除独立 cache 轨后不以新面板补回同等高度。

## 交互与产品边界

### 必须保留

- 四张工具卡及其累计 tokens、费用、breakdown、完整模型信息。
- 7 / 30 / 90 / All 与自定义日期范围。
- 工具颜色身份和当前页面的克制视觉语言。
- 精确 tooltip、数据守恒和 `Legacy unknown` 的识别边界。

### 明确不做

- 新的模型 dashboard 或独立路由。
- 任意维度 Group by、查询语言、可配置 widget。
- 项目、API key、用户、service tier 等组织级筛选器。
- 新统计口径、预测、预算、告警或模型质量评分。
- 让每个模型拥有跨工具永久全局颜色。
- 把 CSV/透视表变成首页默认阅读方式。

## Step 4 的设计命题

下一步原型只需要验证一条核心旅程：

> 在 30 天工具总览中发现某天异常 → 选择 One API → 原图进入模型态且日期不变 → 看见 Top 4、`Legacy unknown`、`其他 N` → 展开完整模型清单并聚焦一个小模型 → 返回工具总览。
